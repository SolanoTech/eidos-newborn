# Возможности

## Две вертикали

Платформа ведёт два вида Золотых записей на общем движке, но с разными правилами
сопоставления и поиска.

| | Физические лица | Юридические лица (мерчанты) |
|---|---|---|
| Ключ сопоставления | Фамилия + имя + дата рождения + ПИНФЛ, запасной вариант — с паспортом | ИНН |
| Поиск | Точный по реквизитам, структурный по нескольким критериям | Точный по ИНН, нечёткий по названию |
| Канал приёма | `/api/v1/client-data`, свой топик Kafka | `/api/v1/legal-data`, свой топик Kafka |
| Идентификатор записи | `GR_<uuid>` | `LE_<uuid>` |

Вертикаль определяется каналом, по которому пришли данные, а не содержимым
сообщения: источник не может подменить тип записи. Подробнее —
[Модель данных](../concepts/data-model.md).

## Приём данных

- **REST** — синхронный ответ по каждой карточке: принято или отклонено с
  перечнем нарушений. См. [Передача по REST](../sources/rest.md).
- **Kafka** — поток сообщений; по одному потребителю на тип сущности, настройки
  меняются без перезапуска. См. [Передача через Kafka](../sources/kafka.md).
- **Авторизация по токену источника** — код источника берётся из токена, а не из
  тела запроса.
- **Сохранение сырья** — каждое сообщение сначала записывается в MongoDB в
  исходном виде.

## Дата-контракты

Для каждой пары «источник + тип сущности» задаётся контракт: путь к полю в
данных источника, целевое поле Золотой записи, тип, формат даты, регулярное
выражение, таблица соответствия значений, значение по умолчанию,
обязательность. Контракт редактируется в консоли и версионируется. См.
[Дата-контракт](../sources/data-contract.md).

## Сопоставление и слияние

- Сопоставление по внешнему идентификатору источника, затем по точному
  совпадению реквизитов. См. [Сопоставление](../concepts/matching.md).
- Слияние по полям с учётом уровня доверия источника (survivorship). См.
  [Слияние и происхождение](../concepts/merge.md).
- Происхождение каждого поля: источник, его уровень доверия, время изменения.
- Версия записи и архив её состояний после каждого изменения.

## Ручной разбор

Очередь незавершённых записей: данные от незарегистрированного источника и
конфликты при равном доверии. Стюард сравнивает значения поле за полем и решает,
что оставить. См. [Незавершённые записи и конфликты](../concepts/conflicts.md).

## Поиск и выдача данных

- Точный поиск физлица по ФИО, дате рождения и ПИНФЛ или паспорту.
- Поиск по идентификатору клиента в системе-источнике.
- Структурный поиск по ПИНФЛ, паспорту, ФИО и телефону.
- Нечёткий поиск мерчанта по названию с учётом транслитерации и
  организационно-правовой формы.
- Привязка и изменение внешних идентификаторов.

## Согласия

Отдельный сервис хранит согласия клиентов (обработка персональных данных,
биометрия, маркетинговые каналы, профилирование, передача третьим лицам),
отвечает, действует ли согласие, и публикует события о выдаче и истечении. См.
[Согласия](../concepts/consents.md).

## Защита персональных данных

- Сопоставление и поиск по ПИНФЛ идут через слепой индекс (HMAC), который
  сохранит работоспособность после токенизации значений.
- Ключи защищены через внешнее хранилище OpenBao; ключ шифрования ключей не
  покидает хранилище.

См. [Защита персональных данных](../concepts/data-protection.md) — там же
описано, что из этого уже действует, а что подготовлено.

## Консоли

- **Консоль администратора**: дашборд, реестр источников, конструктор
  контракта, настройка Kafka, очередь конфликтов, поиск физлиц и юрлиц,
  аудит-лог.
- **Фронт-офис**: поиск клиента и мерчанта, карточки «Клиент 360» и
  «Merchant 360», управление согласиями.

Вход через Keycloak (OpenID Connect). См. [Консоли](../console/login.md).

## Развёртывание

Вся платформа поднимается через Docker Compose: сервисы, PostgreSQL, MongoDB,
Kafka-совместимый брокер Redpanda, Keycloak, OpenBao; Gravitee APIM — отдельным
стеком. См. [Установка](../operations/install.md).
