# Архитектурные решения

Ключевые решения, которые объясняют, почему платформа устроена именно так.
Перед изменением затронутых мест прочтите соответствующее решение; если
предлагаете его пересмотреть, начните с issue.

## Приём

### Тип сущности задаётся каналом

**Решение.** У физлиц и юрлиц разные эндпоинты и разные топики Kafka. В
сообщении типа сущности нет.

**Почему.** Иначе один поток мог бы произвольно менять целевую Золотую запись,
а права и квоты на два потока нельзя было бы настраивать независимо.

**Следствия.** Новая вертикаль — это новый канал на всём пути: эндпоинт
шлюза, `eidos-stage`, ядро, маршруты Gravitee.

### Источник определяется только по токену

**Решение.** Шлюз находит источник по `X-Access-Token` и записывает его код в
данные, заменяя присланное.

**Почему.** Источник не должен иметь возможности выдать себя за другой и
получить чужой уровень доверия.

**Следствия.** Внутренние сервисы доверяют полю `source` — поэтому приём
`eidos-stage` и API ядра нельзя публиковать в обход шлюза.

### Сырьё сохраняется первым

**Решение.** `eidos-stage` записывает карточку в MongoDB до любых
преобразований.

**Почему.** Ни одно сообщение, прошедшее шлюз, не должно потеряться, даже если
обработка дальше сорвётся; исходные данные нужны для разбора и
восстановления.

**Следствия.** Сырьё растёт без ограничений; срок хранения — решение
оператора.

### Две ступени проверки

**Решение.** Шлюз проверяет данные по правилам контракта источника,
`eidos-stage` — по описанию Золотой записи.

**Почему.** Ошибки формата источника возвращаются отправителю как можно раньше
и в его терминах, а ошибки неполного контракта всё равно не пропускаются в
ядро.

### Контракты — данные, а не код

**Решение.** Дата-контракты хранятся в реестре и настраиваются в
конструкторе. Раньше преобразование описывалось классами для каждого
источника.

**Почему.** Подключение источника не должно требовать разработки и
выпуска.

## Слияние

### По-полевое слияние по доверию

**Решение.** Решение принимается для каждого поля: перезаписывает только
источник с более высоким доверием, только непустым и отличающимся значением;
поле запоминает своего владельца.

**Почему.** Неполная карточка надёжного источника не должна стирать данные и
забирать поля, которых не меняла; происхождение каждого значения прозрачно.

### Равное доверие решает человек

**Решение.** При равном доверии и расхождении запись не меняется, входящая
карточка уходит на разбор — одна запись очереди на карточку.

**Почему.** У платформы нет оснований выбрать одно из двух равноценных
значений; дубликаты по полям затопили бы очередь.

### Тот же источник не меняет свои значения

**Решение.** Повторная карточка от источника, которому принадлежит поле, поле
не меняет.

**Следствия.** Источник не может передать обновление собственных данных — это
главное ограничение для потоков изменений и кандидат на пересмотр.

### Общий движок для физлиц и юрлиц

**Решение.** Поток сохранения, создание и слияние — обобщённые классы пакета
`engine`; вертикали отличаются стратегией сопоставления и набором полей.

**Почему.** Правила MDM должны быть одинаковыми для всех видов записей.

### ИНН самодостаточен

**Решение.** Юрлица сопоставляются только по ИНН.

**Почему.** Смена названия мерчанта не должна порождать новую запись.

## Согласия

### Событие — повод свериться

**Решение.** Ядро не берёт состояние согласия из события, а спрашивает
сервис согласий.

**Почему.** Повторная доставка и порядок событий перестают иметь значение,
результат обработки всегда один.

### Истечение — событие о клиенте, а не о строке

**Решение.** `expired` публикуется, только если у клиента не осталось
действующего согласия того же типа; одно событие на пару «клиент + тип».

**Почему.** Потребителю важно, перестал ли клиент быть согласен, а не то, что
закончился срок одной из записей.

### Состояние согласия не меняет версию записи

**Решение.** Состояние согласия и слепой индекс записываются точечным
обновлением, без увеличения версии и времени изменения.

**Почему.** Это внешние факты о клиенте и служебные данные, а не изменение
Золотой записи; иначе массовый досчёт выглядел бы как правка всех клиентов.

## Защита данных

### Слепой индекс без нормализации

**Решение.** Индекс считается от значений как есть, для всех записей.

**Почему.** Индекс заменяет прямое сравнение и обязан давать тот же результат:
любая нормализация изменила бы, какие записи считаются одним человеком.

### KEK не покидает хранилище

**Решение.** Ключи данных заворачиваются в OpenBao через transit; ключ
слепого индекса после разворачивания хранится в памяти процесса.

**Почему.** Компрометация базы не раскрывает ключи. Обращение к хранилищу на
каждую карточку замедлило бы приём, поэтому ключ индекса кешируется — это
осознанный компромисс.

### Хранилище токенов в отдельной схеме

**Решение.** Токены и ключи данных — в схеме `vault`.

**Почему.** Следующий шаг — отдельный пользователь базы с доступом только к
хранилищу, а в целевой картине — отдельный сервис.

## Эксплуатация

### Схемой ядра владеет Flyway

**Решение.** В ядре схема меняется только миграциями, при старте сущности
сверяются со схемой.

**Почему.** Изменение сущности без миграции должно останавливать запуск, а
не расходиться со схемой незаметно.

**Следствия.** Остальные сервисы пока используют `ddl-auto=update` и стартовые
скрипты; в коде отмечено, что с появлением Flyway эти скрипты станут
миграциями.

### Отдельная таблица источников в ядре

**Решение.** Ядро хранит свою таблицу источников с уровнями доверия.

**Почему.** Исторически ядро появилось раньше единого реестра; объединение
отложено.

**Следствия.** Источник регистрируется в двух местах — см.
[Источники, доверие и контракты](../concepts/sources-and-contracts.md#где-хранятся-источники).

### Административные пути консолей через Gravitee

**Решение.** Токен пользователя проверяет Gravitee на краю и подставляет
сервисам `X-Admin-Token`; `eidos-cdi-ui-backend` обслуживает только то, что
требует сведения данных или аудита.

**Почему.** Проверка доступа и маршрутизация вынесены из прикладного кода в
шлюз API.

**Следствия.** Внутренние сервисы доверяют краю. Операции через Gravitee не
попадают в аудит-лог, роль пользователя на этих путях не проверяется. План
развития: передача токена пользователя до сервисов с проверкой прав в них и
аудит через доменные события.

### Приём в eidos-stage на Jackson 2

**Решение.** Тело приёма разбирается собственным `ObjectMapper` Jackson 2, а
не конвертерами Spring MVC на Jackson 3.

**Почему.** Описания записей в `shared-library` и весь конвейер `eidos-stage`
используют Jackson 2; один конвейер — одна версия Jackson.
