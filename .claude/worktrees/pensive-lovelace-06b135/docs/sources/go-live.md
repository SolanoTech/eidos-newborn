# Проверка перед запуском

Перед первичной загрузкой и подключением потока проверьте интеграцию на
тестовых данных. Проверка занимает час-два и экономит дни разбора последствий.

## Подготовьте тестовый набор

Возьмите от 20 до нескольких сотен реальных или максимально похожих карточек
и добавьте к ним заведомо ошибочные:

- без каждого обязательного поля по очереди;
- с неверными форматами: телефон, ПИНФЛ, паспорт, ИНН, даты;
- со значениями, которых нет в таблицах значений, — например, неизвестный код
  пола;
- клиентов, которые уже есть в платформе от других источников.

Если в платформе уже работают другие источники, проверяйте на отдельном стенде
или на клиентах, которых нет в промышленных данных: загруженные данные из
платформы штатно не удаляются.

## Проверьте по шагам

### 1. Токен и контракт

- [ ] Карточка с верным токеном и данными получает `200`.
- [ ] Запрос без токена и с чужим токеном получает `401`.
- [ ] Каждая ошибочная карточка получает `422` с понятным перечнем нарушений
      от шлюза.
- [ ] Ни одна ошибочная карточка не получает ответа
      `GoldenRecord validation failed` — иначе в контракте не хватает правила
      или выражения.

### 2. Результат в Золотой записи

- [ ] Новый клиент находится через
      `GET /api/v1/external/golden-records/search/source-id`.
- [ ] В карточке клиента в консоли все поля заполнены ожидаемыми значениями:
      даты на месте, пол верный, нет «перепутанных» полей.
- [ ] В панели «Происхождение полей» поля закреплены за новым источником.

### 3. Взаимодействие с другими источниками

- [ ] Клиент, который уже есть в платформе, сопоставился с существующей
      записью, а не создал дубликат. Если появился дубликат, сравните написание
      ФИО и дату рождения.
- [ ] Поля обновились так, как ожидается при выбранном уровне доверия.
- [ ] Число новых записей в очереди конфликтов приемлемо.

### 4. Статистика и наблюдение

- [ ] На дашборде у источника растут счётчики «Принято» и «Отклонено» в
      соответствии с отправленным.
- [ ] Команда источника знает, где смотреть причины отказов: ответы REST или
      журнал шлюза для Kafka.

### 5. Kafka (если используется)

- [ ] После включения потребителя в журнале шлюза есть строка
      `Gateway Kafka consumer started: entityType=…`.
- [ ] Тестовые сообщения дошли до Золотых записей.
- [ ] Ошибочное сообщение видно в журнале шлюза
      (`Skipping Kafka message …`) и не блокирует следующие.

### 6. Нагрузка

- [ ] Пробная загрузка объёмом 1–5 % от полного показала приемлемую скорость.
      Оценку полного времени загрузки сообщите владельцу платформы.

## Критерии готовности

- все корректные тестовые карточки приняты;
- все ошибочные карточки отклонены шлюзом с понятными сообщениями;
- дубликатов при сопоставлении с существующими клиентами нет;
- обе стороны понимают, как обрабатываются ошибки и повторы;
- источник зарегистрирован в ядре с согласованным уровнем доверия.

После этого переходите к [первичной загрузке](initial-load.md).
