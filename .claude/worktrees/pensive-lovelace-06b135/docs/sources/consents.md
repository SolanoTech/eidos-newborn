# Передача согласий

Если согласие клиента фиксируется в системе-источнике — например, при
открытии счёта, — источник регистрирует его в платформе через шлюз тем же
токеном, что и для карточек. Модель согласий — [Согласия](../concepts/consents.md).

## Кому принадлежит согласие

Согласие привязывается к **Золотой записи физлица**: в поле `client_uuid`
передаётся её идентификатор. Поэтому порядок такой:

1. Передайте карточку клиента — [Передача по REST](rest.md).
2. Получите идентификатор Золотой записи, например по своему идентификатору
   клиента — [Поиск Золотой записи](../consumers/search.md#по-идентификатору-в-источнике).
3. Зарегистрируйте согласие.

Идентификатор принимается в обеих формах: `GR_<uuid>` и `<uuid>`. Согласия
мерчантов не поддерживаются: идентификатор вида `LE_…` будет отклонён.

## Зарегистрировать согласие

```http
POST /api/v1/consents
X-Access-Token: <токен источника>
Content-Type: application/json

{
  "type": "pd",
  "client_uuid": "GR_5f0c2b1e-8a4d-4c55-9a8e-2b7d4f1c9e10",
  "initial_date": "2026-10-01",
  "end_date": "2027-03-30"
}
```

| Поле | Обязательно | Описание |
|---|---|---|
| `type` | да | Код типа: `pd`, `bio`, `mk_sms`, `mk_push`, `mk_email`, `profiling`, `third_party` |
| `client_uuid` | да | Идентификатор Золотой записи физлица |
| `initial_date` | да | Дата начала действия, `yyyy-MM-dd` |
| `end_date` | нет | Дата окончания включительно. Если не задана: 180 дней от начала для `pd` и `bio`, 365 дней для остальных |

Поле `source_name` передавать не нужно: шлюз подставит код источника из
токена.

Ответ `201`:

```json
{
  "data": {
    "id": "0b8f3c1d-6a2e-4f7b-9d61-3c9e2a7b5f40",
    "client_uuid": "5f0c2b1e-8a4d-4c55-9a8e-2b7d4f1c9e10",
    "start_date": "2026-10-01",
    "end_date": "2027-03-30",
    "type": "pd",
    "source": "bank-1"
  },
  "detail": "Consent created"
}
```

Сохраните `id` — он нужен для отзыва. После регистрации платформа публикует
событие `new`.

| Ответ | Причина |
|---|---|
| `422` `Consent has no client_uuid` | Не передан `client_uuid` |
| `422` `client_uuid is not a golden record identifier: …` | Значение не является идентификатором Золотой записи физлица |
| `422` `Malformed consent body: …` | Тело не является JSON-объектом |
| `422` `<поле>: must not be null` | Не передано обязательное поле |
| `500` с сообщением об ошибке разбора JSON | Неизвестный код в поле `type` |

Повторная регистрация создаёт ещё одно согласие — сервис не проверяет
дубликаты. Действующим считается последнее по дате начала.

## Прочитать согласия клиента

Сводка по всем типам — по каждому типу последнее согласие и признак того,
действует ли оно сегодня:

```http
GET /api/v1/consents/client/{clientId}
X-Access-Token: <токен источника>
```

```json
[
  {"type": "PERSONAL_DATA", "code": "pd", "active": true, "consentId": "0b8f3c1d-…", "startDate": "2026-10-01", "endDate": "2027-03-30"},
  {"type": "BIO", "code": "bio", "active": false, "consentId": null, "startDate": null, "endDate": null}
]
```

Действующее согласие одного типа:

```http
GET /api/v1/consents/active/{clientId}?type=PERSONAL_DATA
X-Access-Token: <токен источника>
```

Ответ `200` — согласие; `404` — действующего согласия этого типа нет. Обратите
внимание: в параметре `type` указывается **имя** типа (`PERSONAL_DATA`, `BIO`,
`MARKETING_SMS` …), а не код.

## Отозвать согласие

```http
POST /api/v1/consents/{id}/revoke
X-Access-Token: <токен источника>
```

Дата окончания переносится на вчерашний день, согласие перестаёт действовать
сразу. Ответ — согласие с новой датой окончания; `404` — согласия с таким `id`
нет.

!!! note "Событие об отзыве может не прийти"
    Отзыв, сделанный в течение дня после ежедневного прохода сервиса согласий,
    в текущей версии не порождает события `expired`. Потребители, которые
    реагируют на отзыв, должны проверять согласие через API — см.
    [Проверка согласия](../consumers/consent-check.md).

Полный справочник — [API eidos-consents](../reference/api/consents.md) и
[Внешний API](../reference/api/external.md#согласия).
