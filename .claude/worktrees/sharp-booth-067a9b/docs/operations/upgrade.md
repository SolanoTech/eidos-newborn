# Обновление версии

Платформа собирается из нескольких репозиториев. Обновление — это переход
всех модулей на новый согласованный набор версий и пересборка образов.

## Перед обновлением

1. Прочтите [примечания к выпуску](../releases.md) и
   [совместимость версий](../reference/compatibility.md): какие модули
   менялись, есть ли миграции и ручные шаги.
2. Сделайте [резервные копии](backup.md) PostgreSQL, MongoDB и OpenBao.
3. Проверьте обновление на стенде с копией данных.
4. Если источники передают данные через Kafka, предупредите их: на время
   обновления приём остановится, непрочитанные сообщения останутся в топиках.
   Источникам на REST нужно уметь повторять запросы — см.
   [Ошибки, повторы, идемпотентность](../sources/errors.md#когда-повторять).

## Порядок

```bash
# 1. Код: каждый репозиторий — на версию из согласованного набора
for dir in . shared-library eidos-core eidos-stage eidos-gateway eidos-consents eidos-cdi-ui-backend eidos-cdi-ui; do
  git -C "$dir" fetch --tags && git -C "$dir" checkout <версия>
done

# 2. Сборка — отдельно, с проверкой результата
docker compose -f docker-compose.yml -f docker-compose.prod.yml build || exit 1

# 3. Остановить приём из Kafka (консоль → Kafka шлюза → выключить,
#    либо PUT /internal/api/v1/kafka-config с "enabled": false)

# 4. Перезапуск сервисов на новых образах
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --force-recreate \
  eidos-core eidos-stage eidos-gateway eidos-consents eidos-cdi-ui-backend eidos-cdi-ui eidos-cdp-ui

# 5. Проверка
docker compose ps
docker compose logs --since 5m eidos-core | grep -iE "flyway|error"
```

Затем включите приём из Kafka и проверьте сквозной путь тестовой карточкой.

## Миграции схемы

| Сервис | Что происходит при старте новой версии |
|---|---|
| `eidos-core` | Flyway применяет новые миграции, затем проверяет, что сущности соответствуют схеме. Если миграция не прошла или схема не совпала, сервис не запустится — в журнале будет причина |
| `eidos-stage`, `eidos-gateway`, `eidos-consents`, `eidos-cdi-ui-backend` | Hibernate добавляет недостающие таблицы и колонки; стартовые скрипты `eidos-stage` и `eidos-gateway` доводят известные ограничения |

Hibernate не обновляет check-ограничения перечислений. Если в примечаниях к
выпуску сказано о новых значениях перечислений — например, новых типах
согласий, — выполните указанные там SQL-команды. Пример —
[Базы данных и миграции](databases.md#сервисы-на-hibernate-ddl-autoupdate).

## Если что-то пошло не так

- **Сборка упала** — контейнеры остаются на прежних образах, если вы не
  запускали `up` после неудачной сборки. Исправьте причину и соберите снова.
- **Ядро не стартует после миграции** — отката миграций нет. Восстановите базу
  `eidos_core` из резервной копии и верните предыдущие версии модулей.
- **Откат версии** — платформа не поддерживает понижение версии на базе,
  прошедшей миграции новой версии. Откатывайтесь на резервную копию,
  сделанную перед обновлением.

## Обновление инфраструктуры

- **PostgreSQL, MongoDB** — обновление основной версии требует выгрузки и
  загрузки данных по процедуре производителя.
- **Keycloak** — обновляется на месте, база мигрируется самим Keycloak.
  Сделайте копию базы `keycloak` заранее.
- **OpenBao, Gravitee** — закрепите версии в compose-файлах и обновляйте
  осознанно, по примечаниям производителя.
- **Redpanda, Kafka** — непрочитанные сообщения сохраняются в томе брокера.
  На стенде у брокера нет тома: сообщения теряются при пересоздании контейнера.
