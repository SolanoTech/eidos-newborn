# События о согласиях

Сервис согласий публикует события в Kafka. Подписка нужна системам, которые
должны реагировать на появление или прекращение согласия: остановить рассылку,
удалить данные у партнёра, обновить витрину.

## Подключение

| Параметр | Значение |
|---|---|
| Топик | `consent-events` (переменная `CONSENT_EVENTS_TOPIC`) |
| Брокер | Брокер платформы. На стенде — `kafka:9092` внутри сети, `localhost:19092` с хоста |
| Ключ | Идентификатор клиента (UUID без префикса) |
| Значение | JSON в UTF-8, без служебных заголовков сериализатора |
| Группа | Своя для каждой системы-потребителя |

Брокер в текущей версии работает без аутентификации — подключайтесь из
внутренней сети. Отдельный токен источника для чтения событий не нужен.

## Формат

```json
{
  "event_type": "expired",
  "client_uuid": "5f0c2b1e-8a4d-4c55-9a8e-2b7d4f1c9e10",
  "type": "mk_sms",
  "start_date": "2025-10-01",
  "end_date": "2026-09-30"
}
```

| Поле | Описание |
|---|---|
| `event_type` | `new` — согласие выдано; `expired` — клиент перестал быть согласен |
| `client_uuid` | Идентификатор Золотой записи без префикса `GR_` |
| `type` | Код типа согласия: `pd`, `bio`, `mk_sms`, `mk_push`, `mk_email`, `profiling`, `third_party` |
| `start_date`, `end_date` | Даты согласия, о котором событие |

Полная спецификация — [Сообщения и события Kafka](../reference/kafka-messages.md#consent-events).

## Семантика

- **`new`** публикуется сразу после регистрации согласия.
- **`expired`** публикуется в двух случаях:
    - сразу после **отзыва** действующего согласия, если у клиента не осталось
      другого действующего сегодня согласия того же типа. В событии — даты
      отозванного согласия, `end_date` — вчерашний день;
    - ежедневным проходом (по умолчанию в 00:05) для клиентов, у которых
      накануне **закончился срок** последнего действующего согласия этого
      типа. Если сервис не работал во время прохода, пропущенные дни
      догоняются при старте или следующем проходе, но не глубже 30 дней.

    Если у клиента осталось другое действующее согласие того же типа, события
    нет. Об одной потере согласия сообщает одно событие: если в день прохода
    согласие пары было отозвано, проход его не повторяет.

- События одного клиента приходят в одну партицию и сохраняют порядок.
- Доставка **не меньше одного раза**: одно событие может прийти повторно.

## Как обрабатывать

Надёжнее всего поступать так же, как ядро платформы: считать событие
**поводом свериться**, а не источником истины.

```python
def on_consent_event(event: dict) -> None:
    # Содержимое события — только подсказка, кого и что перепроверить.
    status = consents_api.active(event["client_uuid"], TYPE_NAMES[event["type"]])
    if status is None:          # 404 — действующего согласия нет
        stop_processing(event["client_uuid"], event["type"])
    else:
        allow_processing(event["client_uuid"], event["type"], until=status["end_date"])
```

Так повторы, порядок событий и пропущенные события не приводят к неверному
состоянию: каждая обработка заново спрашивает актуальный ответ.

!!! warning "Ограничения текущей версии"
    - Если Kafka была недоступна при регистрации или отзыве согласия, событие
      `new` или `expired` теряется: эти события отправляются один раз.
    - Если сервис согласий не работал дольше 30 дней, истечения за более ранние
      дни не публикуются.

    Не полагайтесь только на события: проверяйте согласие через API перед
    обработкой — см. [Проверка согласия](consent-check.md).
