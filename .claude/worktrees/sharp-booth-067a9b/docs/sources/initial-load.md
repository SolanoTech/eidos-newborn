# Первичная загрузка и поток изменений

Подключение источника обычно проходит в два этапа: сначала в платформу
загружается вся накопленная база клиентов, затем передаются изменения. Правила
слияния определяют, в каком порядке загружать источники и чего ждать от потока
изменений.

## Первичная загрузка

### Порядок источников: от менее надёжных к более надёжным

При создании записи **все** её поля, включая пустые, закрепляются за
источником, который её создал. Источник с меньшим доверием потом не сможет
заполнить даже пустые поля. Отсюда правило:

> Загружайте источники **по возрастанию уровня доверия**.

| Порядок | Что получится |
|---|---|
| По возрастанию: сначала `shop` (2), потом `bank` (8) | `shop` создаёт записи со своими данными; `bank` перезаписывает поля, где у него есть отличающиеся значения. Поля, которых у банка нет, остаются со значениями магазина. Полнота максимальная, приоритет у банка |
| По убыванию: сначала `bank` (8), потом `shop` (2) | `bank` создаёт записи; поля, которых у банка нет, остаются пустыми и закреплены за банком. Данные магазина в записи не попадут |

Источники с **равным** доверием загружайте осознанно: каждое расхождение между
ними, включая пустые значения, уйдёт в очередь разбора. Если очередь такого
размера стюардам не по силам, разведите уровни доверия до загрузки.

### Как загружать

- **REST с параллельными запросами** — самый быстрый путь и даёт результат по
  каждой карточке. Отклонённые карточки сразу видны, их можно исправить и
  отправить повторно.
- **Kafka** — удобно, если источник уже публикует данные в топики, но
  обработка идёт в один поток, а об ошибках источник не узнаёт. См.
  [Передача через Kafka](kafka.md).

Повторная отправка тех же карточек безопасна: карточка сопоставится с той же
записью, а одинаковые значения ничего не меняют. Прерванную загрузку можно
продолжить с любого места или запустить заново — при условии, что за это время
источник не начал передавать более свежие изменения тех же клиентов.

### Перед загрузкой

- Пройдите [проверку перед запуском](go-live.md) на выборке из нескольких
  сотен реальных карточек и разберите все отказы.
- Убедитесь, что источник зарегистрирован **в ядре** с правильным уровнем
  доверия: иначе вся загрузка уйдёт в очередь как «неизвестный источник».
- Оцените время загрузки на стенде с похожими ресурсами — см.
  [Производительность](../operations/performance.md).
- Проверьте свободное место: каждая карточка сохраняется в MongoDB как сырьё,
  каждое изменение записи — в архив.

### Как следить за ходом

- Счётчики «принято» и «отклонено» по источнику — на дашборде консоли или в
  `GET /internal/api/v1/ingest-stats`.
- Число Золотых записей — плитка «Golden Records» на дашборде.
- Очередь конфликтов — рост числа конфликтов при загрузке источника с равным
  доверием ожидаем, при загрузке источника с отличающимся доверием — нет.

## Поток изменений

После первичной загрузки источник передаёт новые карточки и изменения
существующих — тем же способом, теми же карточками.

| Событие в источнике | Что произойдёт в платформе |
|---|---|
| Новый клиент | Сопоставление по реквизитам: новая Золотая запись или слияние с существующей |
| Изменились данные клиента, источник **надёжнее** нынешнего владельца поля | Поле обновится |
| Изменились данные клиента, которые **этот же источник** дал раньше | Поле обновится |
| Изменились данные, которые принадлежат источнику с равным доверием | Конфликт на разбор |
| Изменились данные, которые принадлежат более надёжному источнику | Ничего не изменится |

!!! warning "Передавайте изменения одного клиента по порядку"
    Ядро применяет последнюю пришедшую карточку и не сравнивает время
    изменения в источнике. Если две карточки одного клиента обгонят друг
    друга, в Золотой записи останется значение из той, что пришла последней.

    - По REST отправляйте изменения одного клиента последовательно: следующую —
      после ответа на предыдущую. Параллельно можно отправлять карточки разных
      клиентов.
    - В Kafka используйте идентификатор клиента как ключ сообщения: изменения
      одного клиента попадут в одну партицию и сохранят порядок.
    - Не отправляйте повторно старые карточки после свежих — например, при
      повторной загрузке архива.

Очистить поле пустым значением нельзя: пустые значения при слиянии
пропускаются.

### Удаление клиента в источнике

Платформа не принимает удалений: формата «клиент удалён» нет, и Золотые записи
не удаляются через API. Если удаление клиента в источнике должно влиять на
Золотую запись, процесс нужно согласовать с владельцем платформы: штатного
механизма в текущей версии нет.

### Смена идентификатора клиента в источнике

Если источник меняет идентификатор клиента, обновите связку через API,
указав прежнее значение. Иначе новые карточки будут сопоставляться по
реквизитам, а поиск по новому идентификатору ничего не найдёт. См.
[Внешние идентификаторы](../consumers/external-ids.md).
