# Производительность

Готовых цифр производительности нет: она зависит от железа, баз данных и
профиля данных. Ниже — из чего складывается время обработки, что ограничивает
пропускную способность и как измерить её на своём оборудовании.

## Из чего складывается обработка карточки

Каждая карточка проходит синхронную цепочку:

1. шлюз: поиск источника по токену и контракта — два запроса к базе реестра,
   проверка правил;
2. `eidos-stage`: запись сырья в MongoDB, чтение контракта, преобразование,
   проверка;
3. ядро: поиск источника, поиск записи по внешнему идентификатору и по
   слепому индексу, создание или слияние в одной транзакции — запись самой
   записи, строки происхождения на каждое поле, при изменении — копия в архив.

Создание записи физлица порождает около 45 строк в PostgreSQL: запись, связку
и строку происхождения на каждое из 42 полей. Слияние без изменений только
читает данные.

## Что ограничивает

| Ограничение | Следствие | Что делать |
|---|---|---|
| Потребитель Kafka в шлюзе обрабатывает сообщения в одном потоке | Скорость приёма из топика — одна карточка за раз, независимо от числа партиций | Для больших объёмов — REST с параллельными запросами; несколько экземпляров шлюза делят партиции |
| Пул соединений с базой у каждого сервиса — по умолчанию 10 | Предел параллельной обработки на экземпляр | Увеличьте `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE` вместе с ресурсами PostgreSQL |
| Память JVM не настроена | JVM занимает до четверти памяти, видимой контейнеру | Задайте лимит контейнеру и `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75` |
| Одна транзакция на карточку | Нагрузка на PostgreSQL растёт линейно с потоком | Быстрые диски, настройка PostgreSQL под запись |
| Повторная карточка тоже проходит всю цепочку | Повторы и полные выгрузки стоят столько же, сколько новые данные | Передавайте изменения, а не полные выгрузки |

## Как измерить

Каталог `loadtest` репозитория `eidos-infrastructure` содержит инструменты для
сквозной проверки и замера:

| Файл | Назначение |
|---|---|
| `setup.py` | Заводит источник `loadtest`, контракт, регистрирует источники в ядре, включает потребителя Kafka |
| `mocks.py` | Генерирует корректные и ошибочные карточки физлиц и мерчантов |
| `loadtest.py` | Отправляет карточки и измеряет задержку от отправки до появления Золотой записи |
| `merge_test.py`, `merge_test_legal.py` | Проверяют слияние по уровню доверия |
| `produce.py` | Отправляет карточки в Kafka |

Подготовка (нужен Python 3.10+; для режима Kafka — `pip install -r loadtest/requirements.txt`):

```bash
cd loadtest
ADMIN_TOKEN=<токен> python3 setup.py           # физлица
ADMIN_TOKEN=<токен> python3 setup.py --legal   # юрлица
```

Замер:

```bash
python3 loadtest.py --mode rest --count 500 --concurrency 16    # REST, 16 параллельных отправителей
python3 loadtest.py --count 200 --concurrency 8                  # Kafka
python3 loadtest.py --count 1000 --rate 50 --concurrency 16      # ограничение 50 карточек в секунду
python3 loadtest.py --entity legal --mode rest --count 100       # мерчанты
```

| Параметр | Значение по умолчанию | Назначение |
|---|---|---|
| `--mode` | `kafka` | Канал: `kafka` или `rest` |
| `--entity` | `person` | Вертикаль: `person` или `legal` |
| `--count` | 100 | Сколько карточек отправить |
| `--concurrency` | 8 | Параллельных отправителей |
| `--rate` | 0 | Ограничение карточек в секунду, 0 — без ограничения |
| `--timeout` | 60 | Сколько секунд ждать появления одной записи |
| `--interval` | 0.25 | Период опроса ядра, секунды |
| `--bootstrap` | из `config.json` | Адрес брокера |

Скрипт печатает, сколько карточек дошло до Золотых записей, пропускную
способность и распределение задержки: минимум, среднее, медиану, 90-й, 95-й,
99-й процентили и максимум.

Каждая отправленная карточка — новый клиент: замер показывает скорость
создания записей. Слияние дешевле создания.

Скрипт создаёт тестовые записи в базе, и удалить их штатными средствами
нельзя — замеряйте на отдельном стенде.

## Планирование первичной загрузки

1. Измерьте пропускную способность REST на стенде, близком к рабочему, при
   разной параллельности.
2. Разделите объём базы источника на измеренную скорость с запасом в два-три
   раза.
3. Загружайте в окно с низкой нагрузкой и следите за отставанием, ошибками и
   местом на диске — см. [Мониторинг и диагностика](monitoring.md).
