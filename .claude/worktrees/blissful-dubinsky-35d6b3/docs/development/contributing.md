# Как внести вклад

Полные правила — файл `CONTRIBUTING.md` в каждом репозитории. Кратко:

## Лицензия и подпись

- Проект распространяется под Apache License 2.0; отправляя изменения, вы
  соглашаетесь выпустить их под этой лицензией.
- Вместо соглашения о передаче прав используется **Developer Certificate of
  Origin**: подпишите каждый коммит флагом `-s`:

  ```bash
  git commit -s -m "Краткое описание изменения"
  ```

  Имя и адрес в строке `Signed-off-by` должны быть настоящими.

## Процесс

1. Крупное изменение обсудите в issue до начала работы.
2. Ветку создавайте от `main`.
3. Один pull request — одно изменение.
4. Тесты обязательны для нового поведения и исправленных ошибок.
5. Первая строка сообщения коммита — что изменилось, дальше — почему.

## Стиль кода

- Пишите так, как написан окружающий код: те же идиомы, плотность комментариев,
  именование.
- Комментарии в коде — на русском.
- Каждый новый файл с исходным кодом начинается с лицензионного заголовка
  Apache — образец в любом существующем файле.

## Изменения, затрагивающие несколько репозиториев

Модули — отдельные репозитории. Если изменение затрагивает несколько из них —
например, новое поле Золотой записи меняет `shared-library` и `eidos-core`, —
откройте pull request в каждый и сошлитесь в описаниях друг на друга.
Изменения, ломающие совместимость между модулями, сопровождайте обновлением
[совместимости версий](../reference/compatibility.md).

## Документация

Документация лежит в каталоге `docs/` репозитория `eidos-infrastructure` и
собирается MkDocs Material.

- Изменение поведения сопровождайте правкой документации в том же наборе
  pull request.
- Пишите по-русски, коротко и конкретно. Термины — по [глоссарию](../intro/glossary.md).
- Каждая страница — одного типа: обучение, инструкция, объяснение или
  справочник. Не смешивайте объяснение устройства с пошаговой инструкцией.
- Поведение описывайте по коду, а не по замыслу. Если поведение отличается от
  ожидаемого, опишите фактическое и добавьте его в
  [Статус и ограничения](../intro/status.md).
- Перед отправкой соберите сайт в строгом режиме — см.
  [Сборка и тесты](build.md#документация).

## Уязвимости

Не через issue и не через pull request — см.
