# Согласия

Сервис `eidos-consents` хранит согласия клиентов на обработку данных, отвечает
на вопрос «действует ли согласие сейчас» и оповещает остальную платформу об
изменениях.

## Согласие

| Атрибут | Описание |
|---|---|
| Клиент | Идентификатор Золотой записи физлица — UUID без префикса `GR_` |
| Тип | Вид обработки, на который дано согласие |
| Дата начала и окончания | Период действия, включительно |
| Источник | Кто зарегистрировал согласие: код источника или `cdp-console` для выданных в консоли |

### Типы

| Тип | Код в JSON | Имя в параметрах запроса | Срок по умолчанию |
|---|---|---|---|
| Обработка персональных данных | `pd` | `PERSONAL_DATA` | 180 дней |
| Биометрия | `bio` | `BIO` | 180 дней |
| Маркетинг: SMS | `mk_sms` | `MARKETING_SMS` | 365 дней |
| Маркетинг: push | `mk_push` | `MARKETING_PUSH` | 365 дней |
| Маркетинг: e-mail | `mk_email` | `MARKETING_EMAIL` | 365 дней |
| Профилирование | `profiling` | `PROFILING` | 365 дней |
| Передача третьим лицам | `third_party` | `THIRD_PARTY` | 365 дней |

Тип передаётся **кодом** в теле запроса и в событиях, но **именем** в
параметре запроса `type` — так тип разбирают параметры URL. Если дата
окончания не передана, она вычисляется от даты начала по сроку из таблицы.

## Действует ли согласие

Согласие действует в день `D`, если `дата начала ≤ D ≤ дата окончания`. У
клиента может быть несколько согласий одного типа; действующим считается
последнее по дате начала из тех, что действуют сегодня.

Три состояния — согласие не выдавалось, истекло, отозвано — для вопроса
«действует ли» неразличимы: действующего согласия нет, сервис отвечает `404`.

## Отзыв

Отзыв переносит дату окончания на вчерашний день. Запись не удаляется — история
согласий сохраняется. С момента отзыва согласие перестаёт действовать.

## События

Сервис публикует события в Kafka-топик `consent-events` (имя настраивается):

| Событие | Когда | Гарантия |
|---|---|---|
| `new` | Сразу после сохранения нового согласия | Если Kafka недоступна, событие теряется; согласие при этом сохранено |
| `expired` | Ежедневный проход (по умолчанию в 00:05) находит клиентов, у которых вчера закончилось последнее действующее согласие данного типа | Не меньше одного раза: повторный проход за ту же дату и несколько экземпляров сервиса публикуют события повторно |

Событие `expired` означает, что **клиент перестал быть согласен**, а не что
закончилась строка в таблице. Если у клиента есть другое действующее согласие
того же типа, событие не публикуется. На пару «клиент + тип» в день приходится
одно событие, даже если закончилось несколько согласий.

Ключ сообщения — идентификатор клиента, поэтому события одного клиента идут в
одну партицию и сохраняют порядок. Формат — [Сообщения и события Kafka](../reference/kafka-messages.md#consent-events).

!!! warning "Ограничения событий в текущей версии"
    - Отзыв, сделанный после ежедневного прохода, события `expired` не
      порождает: проход ищет согласия, последний день действия которых наступил
      накануне, а отзыв переносит дату окончания на день раньше.
    - Если сервис не работал в момент прохода, события за этот день не
      публикуются: пропущенные дни не догоняются.

    Потребителям, для которых важен отзыв, нужно проверять согласие через API
    непосредственно перед обработкой — см. [Проверка согласия](../consumers/consent-check.md).

## Согласие в Золотой записи

Ядро подписано на события о согласиях. Событие для ядра — **повод свериться**,
а не источник истины: получив событие о согласии на обработку персональных
данных (`pd`), ядро спрашивает у сервиса согласий текущее состояние клиента и
записывает в Золотую запись:

- `pdConsentActive` — есть ли действующее согласие;
- `pdConsentValidTo` — последний день действия;
- `pdConsentCheckedAt` — когда ядро сверялось.

Поэтому повторы и порядок событий значения не имеют. События других типов ядро
пропускает. Если Золотой записи ещё нет — согласие выдали раньше, чем пришли
данные клиента, — состояние не записывается до следующего события по этому
клиенту.

Состояние согласия в записи пока **ничем не используется**: поиск и выдача
данных от него не зависят. Это подготовка к обезличиванию записей клиентов без
действующего согласия — см. [Защита персональных данных](data-protection.md).

## Кто и как работает с согласиями

| Кто | Как |
|---|---|
| Система-источник | Регистрирует согласия и читает их через шлюз — [Передача согласий](../sources/consents.md) |
| Система-потребитель | Проверяет согласие перед обработкой, подписывается на события — [Проверка согласия](../consumers/consent-check.md), [События о согласиях](../consumers/consent-events.md) |
| Оператор | Выдаёт и отзывает согласия в карточке «Клиент 360» — [Фронт-офис](../console/front-office.md) |
