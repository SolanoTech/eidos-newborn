# Дата-контракт

Дата-контракт описывает, где в данных источника лежит каждое значение и во что
оно превращается в Золотой записи. Контракт задаётся на пару
«источник + тип сущности» и редактируется в
[конструкторе контракта](../console/contract-builder.md) или через
[API eidos-stage](../reference/api/stage.md#дата-контракт). Формальная
спецификация — [Формат дата-контракта](../reference/contract-format.md).

## Из чего состоит контракт

```json
{
  "clientIdentifierField": "client_id",
  "fields": [
    {
      "sourceFieldName": "person.birth_date",
      "targetGrField": "GR_BirthDate",
      "dataType": "DATE",
      "required": true,
      "sourceDateFormat": "dd.MM.yyyy",
      "validationRegex": null,
      "defaultValue": null,
      "valueMap": {}
    }
  ]
}
```

- **`clientIdentifierField`** — путь к идентификатору клиента (для юрлиц —
  мерчанта) в данных источника.
- **`fields`** — правила полей. Поля источника, для которых правила нет,
  в Золотую запись не попадают, но сохраняются в сырье.

## Поле-идентификатор

Значение по этому пути становится **внешним идентификатором** записи: по нему
платформа узнаёт клиента при следующей передаче, по нему же источник находит
Золотую запись через внешний API.

- Задайте его обязательно: без идентификатора ядро отклоняет карточку.
- Значение должно быть стабильным и уникальным в пределах источника.
- Путь читается так же, как пути полей, и значение берётся строкой.

## Пути к полям

Путь — имена вложенных объектов через точку: `person.first_name` читает
`{"person": {"first_name": "…"}}`. Пути отсчитываются от объекта `data`
конверта, а не от корня сообщения. Индексы массивов в пути не поддерживаются:
путь указывает на объект, скалярное значение или массив целиком.

## Типы полей

| Тип | Проверка на шлюзе | Преобразование | Когда использовать |
|---|---|---|---|
| `STRING` | Только регулярное выражение, если задано | Значение как есть | Строки, коды, а также дробные числа (`GR_StatutoryFund`) |
| `DATE` | Разбирается по формату даты | Приводится к `yyyy-MM-dd` | Все поля-даты |
| `INTEGER` | Целое число в диапазоне 32-битного целого | Как есть | Числовые коды и счётчики юрлица |
| `BOOLEAN` | `true` или `false` | Как есть | Признаки юрлица: «действует», «банкрот» и другие |
| `GENDER` | Значение должно быть в таблице значений | Через таблицу значений в `M`/`F` | Пол физлица |
| `ARRAY` | Значение должно быть массивом | Массив переносится целиком | Телефоны юрлица (`GR_Phones`) |
| `STRUCT` | Значение должно быть массивом | Массив объектов переносится целиком | Учредители юрлица (`GR_Founders`) |

Типы `ARRAY` и `STRUCT` в текущей версии настраиваются только через API: в
списке типов конструктора их нет.

!!! tip "Логические значения и числа"
    Передавайте логические значения строками `true` и `false` в нижнем
    регистре — шлюз принимает любой регистр, но дальнейшее преобразование
    надёжно только для нижнего. Учтите, что часть числовых полей юрлица
    короткие (`GR_ActivityStateCode`, `GR_KfsCode`, `GR_TaxMode` и другие —
    до 32767): большее значение пройдёт шлюз, но будет отклонено при
    преобразовании.

## Формат даты

Формат задаётся шаблоном Java `DateTimeFormatter`. Значение должно
соответствовать шаблону целиком.

| Значение источника | Шаблон |
|---|---|
| `15.04.1990` | `dd.MM.yyyy` |
| `1990-04-15` | `yyyy-MM-dd` (также используется, если шаблон не задан) |
| `15/04/1990` | `dd/MM/yyyy` |
| `19900415` | `yyyyMMdd` |
| `1990-04-15T00:00:00` | `yyyy-MM-dd'T'HH:mm:ss` |

## Таблица значений

Таблица значений одновременно **перекодирует** значения и задаёт **список
допустимых**:

- если таблица задана, значение источника должно быть одним из её ключей,
  иначе шлюз отклонит карточку: `value 'X' is not allowed for field: …`;
- значение заменяется на соответствующее из таблицы.

Для поля типа `GENDER` таблица обязательна — платформа хранит пол только как
`M` или `F`:

```json
"valueMap": {"1": "M", "2": "F", "M": "M", "F": "F"}
```

Сравнение точное, с учётом регистра: если источник присылает и `m`, и `M`,
добавьте оба ключа.

## Регулярное выражение

Значение проверяется на **полное** совпадение с выражением в синтаксисе Java,
до перекодировки по таблице значений. При несовпадении шлюз отвечает
`field '…' does not match required format`.

Задавайте выражения для полей, у которых формат проверяется в Золотой записи, —
так источник получит понятную ошибку уже на шлюзе:

| Поле | Выражение |
|---|---|
| `GR_Pinfl` | `^\d{14}$` |
| `GR_mobilePhoneMain` | `^998\d{9}$` |
| `GR_docPassData` | `^[A-Z]{2}\d{7}$` |
| `GR_Inn` | `^\d{9}$` |

## Значение по умолчанию

Подставляется, если источник не прислал значение или прислал пустую строку.
Поле с непустым значением по умолчанию не считается пропущенным, даже если оно
обязательное.

Значение по умолчанию **не проходит** перекодировку и разбор даты: задавайте
его сразу в формате Золотой записи — `M` или `F` для пола, `yyyy-MM-dd` для
даты.

## Обязательность

Обязательное поле без значения и без значения по умолчанию даёт ошибку
`missing required field: …`. Отметьте обязательными как минимум правила для
обязательных полей Золотой записи. Если этого не сделать, карточка всё равно
будет отклонена, но позже и с менее понятным сообщением от `eidos-stage`.

## Пример: физлицо

Источник присылает:

```json
{
  "data": {
    "client_id": "LT-00042",
    "phone": "998901234567",
    "first_name": "Дилноза",
    "last_name": "Каримова",
    "middle_name": "Шавкатовна",
    "pinfl": "40312950340021",
    "gender": "2",
    "birth_date": "03.12.1995",
    "citizenship": "Узбекистан",
    "citizenship_id": "860",
    "passport": "AC7654321",
    "passport_issued_by": "ОВД Юнусабадского района",
    "passport_issued_by_id": "26290",
    "passport_issued_date": "11.01.2016",
    "email": "d.karimova@example.uz",
    "address": "г. Ташкент, ул. Тестовая, д. 5"
  }
}
```

Контракт (`clientIdentifierField`: `client_id`):

| Поле источника | Целевое поле | Тип | Обяз. | Формат / выражение / таблица |
|---|---|---|---|---|
| `phone` | `GR_mobilePhoneMain` | `STRING` | да | `^998\d{9}$` |
| `first_name` | `GR_FirstName` | `STRING` | да | |
| `last_name` | `GR_LastName` | `STRING` | да | |
| `middle_name` | `GR_MiddleName` | `STRING` | | |
| `pinfl` | `GR_Pinfl` | `STRING` | да | `^\d{14}$` |
| `gender` | `GR_Gender` | `GENDER` | да | `1→M, 2→F, M→M, F→F` |
| `birth_date` | `GR_BirthDate` | `DATE` | да | `dd.MM.yyyy` |
| `citizenship` | `GR_Citizenship` | `STRING` | да | |
| `citizenship_id` | `GR_CitizenshipId` | `STRING` | да | |
| `passport` | `GR_docPassData` | `STRING` | да | `^[A-Z]{2}\d{7}$` |
| `passport_issued_by` | `GR_docIssuedBy` | `STRING` | да | |
| `passport_issued_by_id` | `GR_docIssuedById` | `STRING` | да | |
| `passport_issued_date` | `GR_docIssuedDate` | `DATE` | да | `dd.MM.yyyy` |
| `email` | `GR_contactsEmail` | `STRING` | | |
| `address` | `GR_addrPermanentAddress` | `STRING` | | |

## Пример: юрлицо

Источник присылает:

```json
{
  "data": {
    "merchant_id": "M-1001",
    "tin": "301234567",
    "name": "ООО \"Оазис Маркет\"",
    "brand": "Оазис Маркет",
    "active": "true",
    "bankrupt": "false",
    "oked": "47110",
    "oked_name": "Розничная торговля в неспециализированных магазинах",
    "reg_date": "21.03.2014",
    "capital": "150000000.00",
    "contacts": {"phones": ["998712001020", "998901112233"]},
    "owners": [
      {"name": "Каримов А.", "pinfl": "31504900120034", "sharePercent": 60},
      {"name": "ООО \"Инвест\"", "inn": "305551112", "sharePercent": 40}
    ]
  }
}
```

Контракт (`clientIdentifierField`: `merchant_id`):

| Поле источника | Целевое поле | Тип | Обяз. | Формат / выражение |
|---|---|---|---|---|
| `tin` | `GR_Inn` | `STRING` | да | `^\d{9}$` |
| `name` | `GR_FullName` | `STRING` | да | |
| `brand` | `GR_ShortName` | `STRING` | | |
| `active` | `GR_IsActive` | `BOOLEAN` | да | |
| `bankrupt` | `GR_IsBankrupt` | `BOOLEAN` | да | |
| `oked` | `GR_OkedCode` | `STRING` | да | |
| `oked_name` | `GR_OkedName` | `STRING` | да | |
| `reg_date` | `GR_RegistrationDate` | `DATE` | | `dd.MM.yyyy` |
| `capital` | `GR_StatutoryFund` | `STRING` | | |
| `contacts.phones` | `GR_Phones` | `ARRAY` | | |
| `owners` | `GR_Founders` | `STRUCT` | | |

Элементы `GR_Founders` должны иметь ключи структуры учредителя: `uuid`,
`name`, `inn`, `pinfl`, `sharePercent`. Остальные ключи отбрасываются.

## Изменение контракта

- Изменения действуют сразу для следующих карточек — согласуйте их с
  интегратором заранее.
- Каждое изменение увеличивает номер версии контракта, но прежние версии не
  сохраняются. Перед существенной правкой сохраните контракт:
  `GET /internal/api/v1/sources/{id}/contract?entityType=PERSON`.
- Новое обязательное правило начнёт отклонять карточки без этого поля сразу
  после сохранения.
