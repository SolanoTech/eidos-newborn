# Статус и ограничения

Eidos CDI развивается открыто. Эта страница перечисляет известные ограничения
текущей версии (основная ветка, октябрь 2026), чтобы вы могли учесть их при
планировании внедрения. Каждое ограничение сопровождается способом обойти его,
если такой есть. Страница обновляется вместе с кодом.

## Зрелость компонентов

| Компонент | Состояние |
|---|---|
| Приём по REST и Kafka, дата-контракты | Работает |
| Сопоставление и слияние физлиц и юрлиц | Работает |
| Очередь ручного разбора | Работает |
| Сервис согласий и события о согласиях | Работает, есть ограничения (см. ниже) |
| Слепой индекс | Работает: на нём идут сопоставление физлиц и поиск по ПИНФЛ |
| Токенизация и шифрование значений | Работает |
| Обезличивание при отзыве согласия | Работает для физлиц, с ограничениями по охвату (см. ниже) |
| Раскрытие по запросу с журналом | Работает |
| Консоль администратора | Работает; часть экранов — макеты (см. [Консоли](../console/login.md)) |
| Фронт-офис | Работают поиск, «Клиент 360», «Merchant 360» и согласия; аналитические блоки — демонстрационные |

## Охват обезличивания

Обезличиваются тринадцать полей Золотой записи физлица. Вне охвата остаётся
следующее, и это осознанные границы текущей версии:

- **Даты** — рождения, выдачи документа, регистрации. Колонки типа `date`:
  замена на токен означала бы смену типа колонки.
- **Справочные значения** — пол, гражданство, национальность, область, район.
  По отдельности человека не определяют, в совокупности остаются
  квазиидентификаторами.
- **Архив и незавершённые записи** — хранят прежние состояния открыто.
- **Записи юрлиц** — ФИО руководителя и ПИНФЛ учредителей не обезличиваются.
- **Сырьё в MongoDB** — полная копия присланного источником, хранится открыто и
  бессрочно.

*Что делать:* ограничьте доступ к базам и задайте сроки хранения сырья и
топиков — см. [Персональные данные](../security/personal-data.md).

### Поиск после обезличивания

Точное сопоставление и поиск по ПИНФЛ целиком работают: они идут по слепому
индексу, посчитанному от открытых значений. **Подстрочный поиск** по фамилии,
имени, отчеству, паспорту и телефону обезличенные записи не находит — слепой
индекс отвечает только на равенство.

### Рост хранилища токенов

Каждый приём карточки на обезличенную запись раскрывает её и обезличивает
заново, создавая новый ключ и новые токены. Прежние остаются в хранилище.
Очистка неиспользуемых токенов пока не реализована.

## Источники и доверие

**Реестр источников и таблица источников ядра разделены.** Источник, заведённый
в консоли или через API `eidos-stage`, автоматически не попадает в ядро.
`eidos-core` хранит собственную таблицу `source` с уровнями доверия, и на слияние
влияет только она. Пока источника нет в этой таблице, ядро отклоняет его
данные. Уровень доверия, заданный в консоли, на слияние не влияет.
*Что делать:* после регистрации источника добавьте его в таблицу ядра —
см. [Регистрация источника](../sources/registration.md#регистрация-в-ядре).

**Флаг «Источник активен» не останавливает приём.** Выключенный в консоли
источник продолжает проходить авторизацию и передавать данные.
*Что делать:* чтобы остановить источник, смените или отзовите его токен.

**Уровень доверия не ограничен по диапазону.** Консоль предлагает значения от
1 до 10, API принимает любое целое число.

## Сопоставление и слияние

**Порядок карточек одного источника не проверяется.** Источник обновляет
принадлежащие ему поля последней пришедшей карточкой. Устаревшая карточка,
пришедшая после свежей, откатит его значения — см.
[Первичная загрузка и поток изменений](../sources/initial-load.md#поток-изменений).

**Источник не может очистить своё поле**: пустые значения при слиянии
пропускаются.

**При равном доверии любое расхождение уходит на разбор.** Сюда относится и
случай, когда одна из сторон прислала пустое значение. Источник с тем же
уровнем доверия не может ни заполнить пустое поле, ни передать неполную
карточку без конфликта.

**Источник с меньшим доверием не заполняет даже пустые поля.** При создании
записи все поля, включая пустые, закрепляются за создавшим источником.

**Внешний идентификатор второго источника не привязывается при слиянии.** Если
карточка источника B совпала с записью источника A по реквизитам, связка
«B — его идентификатор клиента» не создаётся. Поиск по идентификатору B не
найдёт запись, пока связку не создадут явно —
см. [Внешние идентификаторы](../consumers/external-ids.md).

**Сопоставление физлиц только точное.** Фамилия, имя, дата рождения и ПИНФЛ или
паспорт сравниваются на точное равенство, без приведения регистра и пробелов.

**Записи не объединяются.** Две Золотые записи одного человека, если они
появились, средствами платформы слить нельзя.

**История версий недоступна через API.** Архив состояний записи ведётся в базе,
но API и экранов для его просмотра нет.

## Приём данных

**Kafka не даёт обратной связи.** Сообщение, которое не прошло проверку или не
было принято ядром, после нескольких повторов пропускается с записью в журнал
`eidos-gateway`. Очереди недоставленных сообщений (DLQ) нет. Каждая повторная
попытка увеличивает счётчик отклонённых.
*Что делать:* контролируйте статистику приёма и журналы gateway; для
критичных данных используйте REST.

**Срок хранения сырья не ограничен.** Исходные данные в MongoDB не удаляются
автоматически. См. [Персональные данные](../security/personal-data.md).

## Согласия

**События о выдаче и отзыве могут потеряться.** Событие `new` при выдаче и
`expired` при отзыве отправляются один раз, сразу после сохранения. Если Kafka
в этот момент недоступна, ошибка пишется в журнал сервиса, повторной отправки
нет; само согласие и отзыв сохраняются. Ежедневный проход такие события не
восстанавливает. *Что делать:* потребителям, для которых важна каждая смена
состояния, проверять согласие через API перед обработкой — см.
[Проверка согласия](../consumers/consent-check.md).

**Долгий простой догоняется не полностью.** Ежедневный проход догоняет
пропущенные дни, но не глубже 30 дней (`eidos.consents.events.expiry-catch-up-days`):
истечения за более ранние дни не публикуются.

**Состояние согласия на Золотой записи пока не используется.** Ядро записывает,
действует ли согласие на обработку персональных данных, но ни поиск, ни выдача
данных от этого не зависят.

## Безопасность

**API `eidos-core` и `eidos-consents` не защищены аутентификацией.** Их нельзя
публиковать наружу: доступ должен быть только из внутренней сети.
См. [Периметр и угрозы](../security/perimeter.md).

**Любой источник может читать любые Золотые записи** через внешний API шлюза и
менять внешние идентификаторы, указывая в теле запроса код другого источника.

**Внешний API отдаёт служебные поля записи:** номер версии, метки времени,
состояние согласия и значения слепого индекса.

**Токены источников хранятся и показываются открыто** — в базе реестра, в API
и в консоли.

**Персональные данные Золотой записи хранятся в открытом виде.**

## Консоли

**Консоли зависят от Gravitee APIM.** Административные пути консолей
маршрутизируются через Gravitee, а `docker-compose.yml` ожидает сеть
`frontend`, которую создаёт стек Gravitee. Без Gravitee приём и выдача данных
работают, а административные экраны консолей — нет.
См. [Gravitee APIM](../operations/gravitee.md).

**Одна роль на всех.** В Keycloak заведена одна роль `ADMIN`; она нужна и
администратору, и стюарду, и оператору фронт-офиса. Gravitee проверяет подпись
токена, но не роль.

**Аудит-лог фиксирует только операции с согласиями.** Создание источников,
правка контрактов, разбор конфликтов и настройка Kafka в журнал не попадают.

**Часть настроек доступна только через API:** канал Kafka для юрлиц, поля
контракта типов `ARRAY` и `STRUCT`.

**Очередь конфликтов показывает 20 последних записей** — постраничного просмотра
в консоли нет.

**Адрес Keycloak зашит в сборку консолей** (`http://localhost:8180`). Для
развёртывания на сервере образы консолей нужно пересобрать —
см. [Стенд и продуктив](../operations/production.md).

## Эксплуатация

**Миграции схемы есть только у ядра.** `eidos-stage`, `eidos-gateway`,
`eidos-consents` и `eidos-cdi-ui-backend` обновляют схему через Hibernate
`ddl-auto=update` и стартовые скрипты. См. [Базы данных и миграции](../operations/databases.md).

**OpenBao на стенде работает в режиме разработки** и хранит ключи в памяти:
перезапуск контейнера ломает сопоставление. См. [OpenBao](../operations/openbao.md).

**Метрик для систем мониторинга нет.** Сервисы отдают только `GET /health`;
показатели качества данных доступны через API ядра.

**Поставка — только Docker Compose.** Helm-чартов и манифестов Kubernetes нет.
