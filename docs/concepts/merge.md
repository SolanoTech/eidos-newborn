# Слияние и происхождение

Когда входящая карточка сопоставилась с существующей Золотой записью, ядро
решает по каждому полю отдельно: оставить текущее значение или заменить его
входящим. Решение принимается по уровню доверия источников.

## Происхождение поля

Каждое поле Золотой записи закреплено за источником, который дал его текущее
значение. Ядро хранит, какой это источник и когда поле было обновлено. При
создании записи все её поля, включая пустые, закрепляются за создавшим
источником.

Происхождение видно:

- в API ядра: `GET /api/v1/internal/golden-records/{id}/field-meta`;
- в консоли: панель «Происхождение полей» в карточке клиента и мерчанта.

## Правила слияния

Для каждого поля ядро сравнивает входящий источник с источником, которому поле
принадлежит сейчас:

| Входящий источник по отношению к владельцу поля | Значения | Результат |
|---|---|---|
| Другой, доверие **выше** | Входящее непустое и отличается | Поле **перезаписывается**, переходит к входящему источнику |
| Другой, доверие выше | Входящее совпадает с текущим | Значение то же, поле **переходит** к входящему источнику: он подтвердил значение. Версия не меняется |
| Другой, доверие выше | Входящее пустое | Ничего не меняется |
| Другой, доверие **равно** | Различаются (в том числе если одно из них пустое) | **Конфликт**: запись не меняется, входящая карточка уходит на разбор |
| Другой, доверие равно | Совпадают | Ничего не меняется |
| Другой, доверие **ниже** | Любые | Ничего не меняется |
| **Тот же** источник | Входящее непустое и отличается | Поле **обновляется**, остаётся за этим источником |
| Тот же источник | Входящее пустое или совпадает | Ничего не меняется |

Если хотя бы одно поле перезаписано, запись сохраняется с новым номером версии,
а её новое состояние копируется в архив. Если по нескольким полям возник
конфликт, в очередь разбора уходит одна запись на всю карточку.

Итог: источник обновляет значение поля, пока поле принадлежит ему, то есть
пока более надёжный источник не прислал для этого поля своё, отличающееся
значение. Если клиент сменил телефон в CRM и телефон в записи пришёл из CRM,
следующая карточка CRM обновит его. Если телефон уже дал банк с более высоким
доверием, карточка CRM его не изменит.

!!! warning "Порядок карточек одного источника важен"
    Ядро не сравнивает время изменения данных в источнике: применяется
    последняя пришедшая карточка. Если источник отправит устаревшую карточку
    после свежей, например при повторе старого сообщения, принадлежащие ему
    поля откатятся к старым значениям. См.
    [Первичная загрузка и поток изменений](../sources/initial-load.md#поток-изменений).

!!! note "Пустое значение не стирает поле"
    Источник не может очистить своё поле, прислав пустое значение: пустые
    значения при слиянии пропускаются.

## Пример

Запись создана источником `crm` (доверие 5). Затем приходит карточка от `bank`
(доверие 8) с новым телефоном, без e-mail, с тем же ФИО:

| Поле | Было (`crm`, 5) | Пришло от `bank` (8) | Стало | Владелец |
|---|---|---|---|---|
| Телефон | `998901234567` | `998935554433` | `998935554433` | `bank` |
| E-mail | `a@crm.uz` | — | `a@crm.uz` | `crm` |
| Фамилия | `Каримов` | `Каримов` | `Каримов` | `bank` |

Изменённые и подтверждённые значения переходят к более надёжному источнику.
Поля, которые он не прислал, остаются за прежним владельцем: неполная карточка
не стирает значения. В итоге у записи смешанное происхождение — видно, какой
источник отвечает за каждое значение.

Если затем `crm` пришлёт новый e-mail, поле обновится: оно по-прежнему
принадлежит `crm`. Новый телефон или другую фамилию от `crm` ядро
проигнорирует: эти поля теперь принадлежат более надёжному `bank`.

Если карточку присылает `shop` с тем же доверием 5, что у `crm`, и другим
e-mail, возникает конфликт по e-mail: поле принадлежит `crm`, доверие равное.
Телефон `shop` переписать не может.

## Версии и архив

- `version` новой записи равна 0 и растёт на единицу при каждом изменении
  данных: слиянием или решением стюарда.
- После каждого изменения состояние записи целиком копируется в архив
  (`golden_record_archive`, `legal_entity_archive`) с номером новой версии и
  временем.
- Изменения служебных полей — состояния согласия и слепого индекса — версию не
  меняют и в архив не попадают.

Архив позволяет восстановить, как выглядела запись после каждого изменения.
В текущей версии он доступен только запросами к базе данных: API и экрана
истории нет. Исходное состояние при создании в архив не записывается — его
можно восстановить по сырью источника в MongoDB.

## Как спроектировать доверие

- Поставьте выше источники, которые проверяют личность клиента по документам.
- Если два источника одинаково надёжны и вы готовы разбирать их расхождения
  вручную, дайте им равный уровень. Если нет — разведите уровни.
- Помните, что источник с равным доверием конфликтует даже на пустых значениях:
  если он присылает неполные карточки, каждая отличающаяся пустота уйдёт на
  разбор.
- Уровень доверия меняется в двух местах — в реестре и в ядре. См.
  [Источники, доверие и контракты](sources-and-contracts.md#где-хранятся-источники).
