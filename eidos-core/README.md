# eidos-core

Ядро платформы: хранит Золотые записи, сопоставляет с ними входящие данные,
сливает по уровню доверия источника и отдаёт результат потребителям.

## Что делает

**Сопоставление.** Входящую карточку сначала ищут по внешнему идентификатору
источника, затем по точному совпадению реквизитов: фамилия, имя, дата рождения и
ПИНФЛ целиком, с откатом на ту же тройку с паспортом. У юрлиц ключ один — ИНН.

**Слияние по-полевому.** Источник с более высоким уровнем доверия перезаписывает
поле и забирает его происхождение, только если значение пришло непустым и
отличается от текущего. Неизменённые и непришедшие поля остаются за прежним
источником. При равном доверии и расхождении создаётся снимок для ручного
разбора.

**Происхождение.** По каждому полю хранится, какой источник его дал и когда.

**Архив.** Предыдущее состояние записи сохраняется при каждом слиянии.

**Незавершённые записи.** Данные, которые не удалось привязать — от неизвестного
источника или с конфликтом при равном доверии, — попадают в отдельную очередь на
разбор.

**Поиск.** Точный по реквизитам, структурный по нескольким критериям и нечёткий
по названию мерчанта через триграммный индекс.

**Согласия.** Слушает события сервиса согласий и ведёт на записи состояние
согласия на обработку персональных данных. Событие служит поводом свериться:
текущее состояние core спрашивает у сервиса согласий, а не берёт из сообщения.

**Обезличивание.** Пока у клиента есть согласие, персональные значения хранятся
открыто. Как только согласие заканчивается, ядро заменяет тринадцать полей
токенами: значения уезжают в зашифрованное хранилище, в карточке остаются
ссылки. Возвращённое согласие раскрывает их обратно. Источник может продолжать
присылать карточки, ничего не зная о форме хранения: на время слияния запись
раскрывается и обезличивается снова, всё в одной транзакции.

**Поиск после обезличивания** работает: сопоставление и точный поиск идут по
слепому индексу — HMAC над теми же комбинациями полей, посчитанный от открытых
значений и не меняющийся при токенизации.

**Криптоконтур.** Ключ данных генерируется Tink, заворачивается ключом из
OpenBao и хранится только в защищённом виде. Сам ключ шифрования ключей из
хранилища не выходит.

**Раскрытие по запросу** — исключение, оставляющее след: требует указания
запрашивающего и основания, каждое раскрытое поле попадает в журнал.

## Установка

```bash
docker compose up -d eidos-core
```

Поднимет заодно PostgreSQL, Kafka и OpenBao. Отдельно, без приложения:

```bash
docker compose up -d postgres kafka openbao
```

Локально из исходников (нужны JDK 26 и установленная `shared-library`):

```bash
mvn -f shared-library/pom.xml clean install
cd eidos-core && ./mvnw spring-boot:run
```

Тесты:

```bash
cd eidos-core && ./mvnw test
```

Проверка криптоконтура на поднятом стенде описана в javadoc
`TokenVaultStandTest`.

## Конфигурация

`src/main/resources/application.properties`; в контейнере переопределяется
переменными окружения (точка меняется на подчёркивание, регистр верхний).

| Ключ | Назначение |
|---|---|
| `server.port` | порт сервиса, по умолчанию `8080` |
| `spring.datasource.url` | база Золотых записей |
| `spring.datasource.username` / `.password` | доступ к базе |
| `spring.flyway.baseline-on-migrate` | позволяет существующей базе присоединиться к миграциям |
| `eidos.consents.base-url` | адрес сервиса согласий |
| `eidos.consents.events.topic` | топик событий о согласиях |
| `eidos.consents.events.group-id` | группа потребителя |
| `eidos.consents.events.enabled` | включение потребителя |
| `spring.kafka.bootstrap-servers` | адрес брокера |
| `eidos.crypto.openbao.base-url` | адрес хранилища ключей |
| `eidos.crypto.openbao.token` | токен доступа к хранилищу |
| `eidos.crypto.openbao.kek-name` | имя ключа шифрования ключей |
| `eidos.crypto.enabled` | включение криптоконтура |
| `eidos.crypto.blind-index.backfill-enabled` | досчёт слепого индекса при старте |
| `eidos.crypto.blind-index.batch-size` | размер пачки досчёта |
| `eidos.crypto.depersonalisation.sweep-enabled` | страховочный проход по рассогласованным записям |
| `eidos.crypto.depersonalisation.sweep-cron` | расписание прохода |
| `eidos.crypto.depersonalisation.batch-size` | размер пачки прохода |

Схемой владеет Flyway, `ddl-auto` выставлен в `validate`: изменение сущности без
миграции роняет приложение на старте.

## Эндпоинты

### Внешние — для систем-потребителей

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/v1/external/golden-records/search/accurate` | точный поиск: `firstName`, `lastName`, `birthDate` и `pinfl` либо `passport` |
| `GET` | `/api/v1/external/golden-records/search/source-id` | поиск по идентификатору в системе-источнике: `source`, `source_id` |
| `POST` | `/api/v1/external/golden-records/{uuid}/external-id` | привязать внешний идентификатор |
| `PUT` | `/api/v1/external/golden-records/{uuid}/external-id` | изменить внешний идентификатор |
| `PUT` | `/api/v1/external/golden-records/external-id` | изменить внешний идентификатор по прежнему значению |

### Внутренние — физические лица

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/internal/golden-records` | приём карточки: создание или слияние |
| `GET` | `/api/v1/internal/golden-records/search` | поиск по образцу, параметры `query`, `page` |
| `GET` | `/api/v1/internal/golden-records/search/structured` | поиск по реквизитам: `pinfl`, `passport`, `lastName`, `firstName`, `middleName`, `phone` |
| `GET` | `/api/v1/internal/golden-records/{clientId}` | карточка целиком |
| `GET` | `/api/v1/internal/golden-records/{clientId}/field-meta` | происхождение полей |
| `GET` | `/api/v1/internal/golden-records/{clientId}/external-ids` | идентификаторы в системах-источниках |
| `POST` | `/api/v1/internal/golden-records/{clientId}/reveal` | раскрыть значения обезличенной записи: требует `actor` и `reason` |

ПИНФЛ в структурном поиске сопоставляется целиком: сравнение идёт по слепому
индексу, который умеет только равенство. Остальные критерии остались
подстрочными.

### Внутренние — юридические лица

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/internal/legal-records` | приём карточки мерчанта |
| `GET` | `/api/v1/internal/legal-records/search/inn` | точный поиск по ИНН |
| `GET` | `/api/v1/internal/legal-records/search/name` | нечёткий поиск по названию |
| `GET` | `/api/v1/internal/legal-records/{grLegalEntityId}` | карточка целиком |
| `GET` | `/api/v1/internal/legal-records/{grLegalEntityId}/field-meta` | происхождение полей |
| `GET` | `/api/v1/internal/legal-records/{grLegalEntityId}/external-ids` | идентификаторы в системах-источниках |

### Внутренние — разбор и наблюдение

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/v1/internal/tentative` | очередь незавершённых записей физлиц |
| `GET` | `/api/v1/internal/tentative/count` | размер очереди |
| `POST` | `/api/v1/internal/tentative/{id}/resolve` | разбор записи |
| `GET` | `/api/v1/internal/tentative-legal` | та же очередь для юрлиц |
| `GET` | `/api/v1/internal/tentative-legal/count` | размер очереди |
| `POST` | `/api/v1/internal/tentative-legal/{id}/resolve` | разбор записи |
| `GET` | `/api/v1/internal/metrics` | метрики качества данных |
| `GET` | `/health` | проба живости |
