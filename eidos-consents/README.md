# eidos-consents

Сервис согласий: хранит согласия клиентов на обработку данных, отвечает на
вопрос «действует ли согласие сейчас» и оповещает остальную платформу об
изменениях.

## Что делает

**Хранит согласия** с указанием типа, срока действия и источника, от которого оно
получено. Типы: обработка персональных данных, биометрия, маркетинговые каналы
(SMS, push, e-mail), профилирование, передача третьим лицам.

**Считает срок.** Если дата окончания не передана, она вычисляется от начальной:
полгода для персональных данных и биометрии, год для остальных типов.

**Отзыв** обрезает срок действия вчерашним днём, сохраняя историю. Поэтому три
состояния — не выдавалось, истекло, отозвано — выглядят одинаково: действующего
согласия нет.

**Излучает события** в Kafka. Выдача согласия даёт событие `new` сразу после
фиксации, отзыв действующего согласия — `expired`, тоже сразу. Согласия, у
которых закончился срок, раз в сутки находит планировщик и даёт по ним
`expired`; пропущенные из-за простоя дни он догоняет.

Событие об истечении означает, что **клиент перестал быть согласен**, а не что
закончилась строка в таблице: если у клиента есть другое действующее согласие
того же типа, событие не излучается. На пару «клиент + тип» приходится ровно одно
событие, даже если в один день закончилось несколько согласий.

Идентификатор клиента в согласии — это идентификатор Золотой записи.

## Установка

```bash
docker compose up -d eidos-consents
```

Поднимет заодно PostgreSQL и Kafka. Отдельно, без приложения:

```bash
docker compose up -d postgres kafka
```

Локально из исходников (нужен JDK 26):

```bash
cd eidos-consents && ./mvnw spring-boot:run
```

Тесты:

```bash
cd eidos-consents && ./mvnw test
```

## Конфигурация

`src/main/resources/application.properties`; в контейнере переопределяется
переменными окружения.

| Ключ | Назначение |
|---|---|
| `server.port` | порт сервиса, по умолчанию `8082` |
| `spring.datasource.url` | база согласий |
| `spring.datasource.username` / `.password` | доступ к базе |
| `spring.kafka.bootstrap-servers` | адрес брокера |
| `eidos.consents.events.topic` | топик событий |
| `eidos.consents.events.enabled` | включение публикации |
| `eidos.consents.events.expiry-cron` | расписание прохода по истёкшим согласиям |

На хосте сервис отдан на порт **8086**: 8082 занят сторонним стеком.

## Эндпоинты

Внутренний API, открыт внутри кластера. Наружу источникам он отдаётся через
eidos-gateway, который добавляет проверку токена источника.

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/internal/api/v1/consents` | зарегистрировать согласие |
| `GET` | `/internal/api/v1/consents/active/{client_uuid}` | действующее согласие одного типа, параметр `type`; `404` если действующего нет |
| `GET` | `/internal/api/v1/consents/client/{client_uuid}` | сводка по всем типам с признаком действия |
| `POST` | `/internal/api/v1/consents/{id}/revoke` | отозвать согласие |
| `GET` | `/health` | проба живости |

Тип согласия в теле запроса передаётся коротким кодом (`pd`, `bio`, `mk_sms`,
`mk_push`, `mk_email`, `profiling`, `third_party`), а в параметре запроса — именем
константы (`PERSONAL_DATA`, `BIO`, …).

## Формат события

Ключ сообщения — идентификатор клиента, поэтому события одного клиента сохраняют
порядок между собой.

```json
{
  "event_type": "new",
  "client_uuid": "7f4ea435-3e76-4a80-8c39-d35134090b0f",
  "type": "pd",
  "start_date": "2026-03-01",
  "end_date": "2026-08-27"
}
```

Тип события — `new` или `expired`. Доставка at-least-once: повторный проход
планировщика излучит событие заново, поэтому потребитель должен быть идемпотентен.
